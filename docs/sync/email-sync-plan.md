# 邮箱账号与网页 / App 共用数据

状态：邮箱登录、账号隔离缓存、同步接口和首次导入检查已实现于独立分支；尚未连接真实 Supabase，尚未上线登录或同步。配置步骤见 USER-SETUP.md。

## 实施顺序

1. 共用底层：Supabase Auth 邮箱密码；同一个项目数据库；以认证后的 user_id 隔离数据。
2. 网页先贯通：注册、验证邮箱、登录、退出、重置密码；任务创建、修改、完成、删除与跨浏览器验证。
3. App 接同一服务：保持现有本地来源和数据；增加网络能力后发布一次原生升级，验证手机与网页互相修改。
4. 接项目与复盘，再完成离线队列重试、冲突处理和故障验证。

## 共用数据约定

- 记录键为 user_id + kind + item_id；kind 为 tasks / projects / reviews。旧任务、项目 ID 和复盘日期保持不变，payload 保留未知字段。
- 写入由服务端认证身份，不能相信客户端传来的 user_id；所有公开表开启 RLS，其他账号和未登录请求禁止访问。
- 每条记录有服务端 version。写入携带 expectedVersion；不匹配返回冲突，保留本地编辑供用户选择。不能用整份数组互相覆盖。
- 每次写入携带稳定 mutationId，超时重试复用同一个值；服务端幂等。删除使用 tombstone，不能让离线旧数据复活。
- 首版以前台进入、恢复网络和写入后主动刷新为基础；实时订阅只负责通知重新拉取，不是可靠同步队列。
- 本地缓存、待上传操作和拉取游标按账号分区；切换账号不得把上个账号的数据带入新账号。
- 现有 mobile_pending_v1 仅是脏键标记，不可当作逐条操作队列直接上传。

## 首次导入

先导出本地备份，再拉取完整云端记录（含删除标记），使用 shared-sync/import-plan.mjs 生成创建、相同、冲突三类。先展示统计，再由用户确认导入账号。缺失 ID、重复 ID 或损坏内容阻止导入；旧版 daily_reviews_v1 另做显式迁移，保留原始备份。不得清空本地数据或默默覆盖冲突。

## 用户需配置

登录 https://supabase.com/dashboard 并创建项目。部署时配置项目 URL 和 Publishable Key，密钥通过安全配置渠道填写；数据库密码、Secret Key、service_role 不进入前端、App 或聊天。配置邮箱验证、重置密码回跳域名；正式邮件发送需验证 SMTP。手机常用网络需实测访问性。

## 上线门槛

验证两个账号相互不可读写；未登录禁止访问；过期登录后可恢复；同一 mutationId 重试不重复创建；并发编辑不丢数据；删除后离线重连不复活；导入中断可续传；退出切号不泄露缓存；手机和网页互相新增、完成、删除同步。当前导入单测不代表这些云端检查已通过。

官方参考：https://supabase.com/docs/guides/auth/passwords 、https://supabase.com/docs/guides/database/postgres/row-level-security 。本方案替代 mobile/architecture.md 中未来使用 Redis 会话与云存储的设想；当前本地模式保持不变。
